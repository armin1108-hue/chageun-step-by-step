## 5. 과제 1 — 강사 시연의 모든 작업

### A. 기획과 Stitch 화면 설계

**01. 기존 프로젝트를 연다.** 링크로 접속한 뒤 프로젝트 이름이 ‘차근차근 특수교육 일과 도우미’인지 확인한다.

**02. 대상과 문제를 설명한다.** 학생은 일과를 확인하고 자신의 의사를 표현한다. 교사는 기록을 확인하며 필요한 지원을 제공한다. 학부모는 하루의 성취를 이해한다.

**03. 사용자 흐름을 보여준다.** 처음→나의 하루→마음 전하기→교사 확인의 순서를 설명한다. 그린 화면과 실제 연결된 기능을 구분한다.

**04. 오늘 구현할 범위를 고른다.** 일과 완료 체크, 기분 선택·기록, 같은 브라우저에서 기록 확인의 3개 기능을 중심으로 보여준다. 다기기 실시간 동기화와 외부 전송은 별도 구현 범위다.

**05. 최초 요청의 핵심을 재현한다.** 아래 예시를 사용한다. 이는 과거 원문을 복원한 것이 아니라 현재 화면 구성을 바탕으로 재구성한 교육용 요청문이다.

```text
특수학급 학생이 자신의 일과를 확인하고 마음을 표현하는 ‘차근차근’ 웹앱을 설계해줘. 한국어, 큰 글자와 넓은 터치 버튼, 차분한 색상을 사용해줘. 우선 처음·나의 하루·마음 전하기 3개 화면을 만들어줘. 나의 하루에는 가방 정리, 인사, 수업, 점심, 귀가 5개 일과를 넣고, 마음 전하기에는 기분을 선택하고 화면에 크게 표시하는 버튼을 넣어줘. 가상자료를 사용하고 검증하지 않은 인증·보안·효과 주장은 넣지 말아줘.
```

**06. 수정 요청을 보여준다.** 이미 있는 화면을 활용해 수정 전후를 비교한다.

```text
현재 화면의 목적과 구성을 유지해줘. 터치할 버튼을 크게 하고, 선택 상태를 색과 글자로 함께 표현해줘. 학생용과 교사용 화면을 구분해줘. 실제 구현하지 않은 ‘실시간 전송·암호화 완료·인증’ 표현은 제거하고 ‘실습용 가상자료’라고 표시해줘.
```

강사용 멘트: “화면을 많이 만드는 것보다 누가 어떤 순서로 사용하는지를 정하는 것이 먼저입니다. 학생은 일과를 확인하고 완료를 표시합니다. 교사는 그 기록을 보고 지원합니다. 화면에 버튼이 있다고 해서 기능이 연결된 것은 아니므로 내보낸 코드를 사용해 확인하겠습니다.”

### B. 코드 내보내기와 기능 구현

**07. 필요한 화면을 선택한다.** 캔버스에서 하나를 선택하고 여러 화면은 화면에 표시되는 선택 방법을 따른다. 무조건 전체 선택하지 않는다. 현재 프로젝트는 전체 선택 시 최대 16개 제한이 표시된다.

**08. 우측 상단 Export를 누른다.** 아무 화면도 선택하지 않았다면 ‘No screens selected’가 나온다. 화면을 선택한 뒤 다시 진행한다.

**09. .zip을 선택하고 Export한다.** 또는 Code to Clipboard→Copy로 HTML을 복사한다. 오늘은 GitHub 과정을 배우므로 Netlify PREVIEW로 직접 이동하는 경로와 구분해 설명한다.

**10. 파일이 실제로 저장되었는지 확인한다.** ZIP 다운로드가 완료된 파일을 확인하고 압축을 푼다. 코드 복사는 텍스트 편집기에 붙여넣어 HTML이 들어왔는지 확인한다. 버튼 클릭만으로 내보내기 성공이라고 판단하지 않는다.

**11. 내보낸 폴더의 내용을 확인한다.** HTML·CSS·JS·이미지, `package.json` 여부를 살핀다. 생성된 가이드의 폴더 구조와 실제 다운로드 파일은 다를 수 있다.

**12. 메인 진입 파일을 정한다.** 정적 HTML 방식에서는 첫 화면을 `index.html`로 두고 저장소 루트에 놓는다. 다른 화면은 실제 파일명과 경로를 표로 정리한다.

**13. 메뉴와 버튼을 시험한다.** `href="#"`인 링크, 클릭해도 바뀌지 않는 버튼, 고정된 완료율 등을 찾는다. 정상 기능은 보존하고 부족한 부분만 구현한다.

**14. AI 개발 도구에 기능 구현을 요청한다.** 내보낸 실제 코드 또는 ZIP을 제공하고 다음을 요청한다. 사용 중인 AI 환경에서 파일 생성·코드 수정이 가능한 방식을 사용한다.

```text
첨부한 Stitch 코드를 기반으로 배포 가능한 웹앱을 완성해줘. 디자인과 정상 기능은 유지하고 미구현 부분만 수정해줘. 오늘은 HTML·CSS·JavaScript 방식으로 구현하고 불필요한 빌드 단계는 추가하지 말아줘. index.html에서 시작하도록 하고 메뉴의 # 링크를 실제 화면 이동으로 연결해줘. 일과 완료 체크와 기분 기록이 같은 브라우저의 localStorage에 저장되고 새로고침 후 유지되게 해줘. 교사 화면에서 같은 브라우저의 기록을 확인하게 해줘. 기록은 이 기기에만 저장된다는 안내를 넣어줘. 외부 전송·여러 기기 동기화·AI 분석은 연결하지 않았다면 작동하는 것처럼 표시하지 말아줘. README.md와 정적 사이트용 netlify.toml을 작성하고 .gitignore에 .netlify/를 넣어줘. 실행·확인 방법과 실제 생성 파일 목록을 알려줘.
```

**15. 핵심 기능 3개를 시험한다.** 일과 한 개 체크→완료 수 변경, 기분 선택→기록 표시, 새로고침→기록 유지, 교사 화면→같은 기록 표시를 차례로 확인한다.

**16. 오류를 구체적으로 수정한다.** “안 돼요”보다 화면·버튼·현재 결과·원하는 결과를 알려준다.

```text
나의 하루 화면에서 ‘점심’ 완료 버튼을 눌러도 완료 수가 바뀌지 않는다. 버튼 상태와 완료 수가 함께 갱신되고 새로고침 후에도 유지되게 수정해줘. 수정 파일과 확인 순서를 알려줘.
```

강사용 멘트: “Stitch의 결과를 가져와 화면 이동과 기록 저장을 연결하는 단계입니다. 한 기기에서 기록을 보여주는 실습과 여러 사람이 동시에 사용하는 서비스는 저장 방식이 다릅니다. 오늘 구현된 범위를 먼저 완성하고 실제로 눌러 확인하겠습니다.”

### C. GitHub 저장과 공유

**17. GitHub에서 새 저장소를 만든다.** New repository를 선택한다. 강사용 예시 이름은 `chageun-demo`, 개인 과제는 `my-app-영문이름`이다. 예시 이름은 실제 생성되었다는 의미가 아니다.

**18. 설명과 공개 범위를 정한다.** 공유용 가상자료 실습 코드는 Public으로 만들 수 있다. Private을 선택하면 강사·동료에게 별도 접근 권한을 부여해야 저장소를 열 수 있다. 배포 URL 공개 범위는 Netlify에서 별도로 확인한다.

**19. 저장소를 생성한다.** README를 포함해 생성하면 이후 파일 업로드 메뉴를 찾기 쉽다.

**20. Add file→Upload files를 연다.** ZIP 자체가 아니라 압축을 푼 실제 실행 파일과 자산 폴더를 업로드한다. 준비한 폴더의 내용이 저장소에서 올바른 구조로 배치되는지 확인한다.

**21. README와 .gitignore를 포함한다.** README에는 목적·기능·실행 방법·기록 저장 범위·배포 링크·보완사항을 적는다. 실제 학생 자료, API 키, 비밀번호를 실습 코드에 넣지 않는다. `.netlify/`는 Git에 포함하지 않는다.

**22. Commit changes로 변경을 저장한다.** 커밋 메시지 예: `첫 번째 작동 버전 업로드`. 새 브랜치를 선택했다면 Pull request를 만들어 배포 기준 브랜치에 합친다.

**23. 실제 저장소 화면을 확인한다.** 배포 기준 브랜치에서 `index.html` 또는 프로젝트의 실제 빌드 파일이 보이는지 확인한다. 학생이 만든 파일은 다른 저장소에 따로 두어 과제별 변경을 구분한다.

**24. 저장소 주소를 복사한다.** 이 주소는 코드를 읽고 수정 내용을 확인하는 주소다. 사용자가 앱을 실행하는 배포 URL과 구분해 설명한다.

강사용 멘트: “GitHub에는 앱을 만드는 파일과 수정 이력을 저장합니다. 지금 복사하는 주소는 코드 공유 주소입니다. 다음 단계에서 Netlify가 이 저장소를 읽고 사람들이 접속할 실행 주소를 만들어 줍니다.”

### D. Netlify 배포와 수정 재배포

**25. Netlify 팀의 Projects 화면을 연다.** Add new project→Import an existing project를 선택한다.

**26. Git provider에서 GitHub를 선택한다.** 필요한 연결·권한 설정을 완료하고 실습 저장소가 목록에 표시되는지 확인한다.

**27. 방금 만든 저장소를 고른다.** 이름이 비슷한 다른 저장소를 선택하지 않도록 GitHub에서 확인한 주소와 대조한다.

**28. 배포 기준 브랜치와 빌드 설정을 확인한다.** 아래 표는 실제 파일 구조에 따라 선택한다. 모든 프로젝트에 `npm run build`와 `dist`를 입력하지 않는다.

| 실제 파일 구조 | Build command | Publish directory | 추가 확인 |
| --- | --- | --- | --- |
| 저장소 루트에 index.html·CSS·JS | 비워 둠 | `.` | 별도 컴파일이 필요 없는 정적 사이트 |
| 정적 파일이 public 폴더에 모두 있음 | 비워 둠 | `public` | public/index.html과 모든 자산 포함 |
| package.json의 build 스크립트가 Vite 빌드를 실행하며 dist 생성 | `npm run build` | `dist` | 실제 build 스크립트·의존성·출력 경로 확인 |
| 그 밖의 프레임워크 | 해당 프로젝트의 명령 | 실제 출력 폴더 | 자동 제안값과 프로젝트 설명 대조 |

**29. Deploy를 실행한다.** 빌드·배포 화면을 열고 성공 또는 오류 상태를 확인한다. ‘빌드 중’은 완료가 아니다.

**30. 실제 배포 URL을 연다.** Netlify 화면에 표시된 URL을 사용한다. 이름을 추측해 주소를 만들지 않는다. 새 탭과 스마트폰에서 열어 접근 권한도 확인한다.

**31. 배포된 사이트에서 기능을 다시 시험한다.** 화면 이동, 입력, 저장, 새로고침, 이미지 표시를 확인한다. 로컬 파일과 배포 사이트는 저장 공간이 달라 로컬에서 입력했던 기록이 배포 사이트로 자동 옮겨지지 않는다.

**32. GitHub에서 문구 하나를 수정한다.** `index.html` 또는 해당 소스 파일을 열고 편집 버튼을 눌러 첫 화면의 소개 문구를 바꾼다. 커밋 메시지 예: `첫 화면 안내 문구 개선`.

**33. Netlify에서 재배포를 확인한다.** 배포 기준 브랜치에 반영된 변경이 새 배포를 시작하는지 확인한다. 새 배포가 성공한 후 기존 URL을 새로고침해 문구 변경을 확인한다. 브랜치가 다르거나 자동 게시가 중지된 경우 해당 설정을 확인한다.

**34. README에 배포 URL을 추가한다.** 코드 URL과 실행 URL을 함께 기록한다. 배포된 사이트가 로그인이나 팀 권한으로 보호되면 동료에게 필요한 접근 방법을 안내한다.

강사용 멘트: “정적 HTML이라면 배포 전에 파일을 새로 만드는 빌드 과정이 필요하지 않습니다. 반면 Vite 같은 프로젝트는 소스에서 배포용 파일을 만드는 명령이 필요합니다. 같은 설정을 무조건 따라 입력하지 말고 자신이 가진 파일에 맞추어야 합니다. 이제 GitHub에서 문구를 바꾸고 같은 앱 주소에 바뀐 내용이 올라오는지 확인하겠습니다.”

## 6. 과제 2 — 개인 개발과 학습동아리 게시

**35. 개인 문제를 한 문장으로 정한다.** “누가 어떤 일을 더 쉽게 하도록 만들 것인가?”에 답한다.

**36. 핵심 기능 2~3개를 선택한다.** 예: 자료 목록·검색·즐겨찾기, 일과 등록·완료 체크·완료율, 활동 입력·기록 조회·내보내기.

**37. Stitch로 화면 1~3개를 만든다.** 아래 프롬프트를 사용한다.

```text
나는 [직무·역할]이다. [사용 대상]이 [해결할 문제]를 해결하는 [앱 이름]을 만들고 싶다. 핵심 기능은 [기능 1], [기능 2], [기능 3]이다. 한국어 반응형 웹앱으로 화면 1~3개를 설계해줘. 각 버튼의 목적과 화면 이동을 명확히 하고 가상자료 3개를 넣어줘. 사용자가 처음 방문해 무엇을 해야 하는지 알 수 있게 해줘.
```

**38. 코드로 내보내고 기능을 연결한다.** 과제 1의 07~16단계를 적용한다. AI 요청의 앱 이름과 기능만 개인 과제에 맞추어 바꾼다.

**39. 개인 GitHub 저장소를 만들고 Netlify로 배포한다.** 17~34단계를 수행한다. 다른 사람의 저장소를 자신의 제출 주소로 사용하지 않는다. 디자인을 반복 생성하기보다 한 번 확정한 디자인의 기능을 보완한다.

**40. 동료에게 사용을 부탁한다.** “핵심 기능을 한 번 사용해 보고 막힌 위치를 알려 주세요.”라고 요청한다. 수정 후 같은 배포 주소에서 동작을 재확인한다.

**41. 학습동아리 방에 게시한다.** 아래 양식을 복사해 채운다. 게시 예시는 실제 발송된 메시지가 아니다.

```text
[4일차 개인 앱·웹 개발 과제]
이름:
앱·웹 이름:
사용 대상:
해결하려는 문제:

배포 URL:
GitHub 저장소 URL:
Stitch 프로젝트 URL 또는 화면 이미지:

실제로 작동하는 기능:
1.
2.
3.

사용 방법:
기록 저장 방식: 이 기기 / 공용 DB / 저장 없음 중 해당 사항 설명
사용 시험 결과:
수정한 내용:
남은 보완사항:

동료에게 부탁할 피드백:
핵심 기능을 사용해 보시고 불편한 점 한 가지를 알려 주세요.
```

**42. 제출을 확인한다.** 링크가 열리는지, GitHub를 열람할 수 있는지, 게시글에 사용 방법과 구현 범위가 있는지 확인한다.

## 9. 완료 기준과 후속 안내

오늘의 최소 완료 기준:

- 본인의 개발 목적을 설명할 수 있다.
- Stitch로 설계한 화면 또는 프로젝트가 있다.
- 핵심 기능 2개 이상이 실제로 작동한다.
- 본인의 GitHub 저장소에 코드와 README가 있다.
- Netlify 배포 URL을 다른 사람이 열 수 있다.
- 수정 1건을 커밋하고 재배포 반영을 확인했다.
- 학습동아리 방에 두 URL·사용 방법·보완사항을 게시했다.

학습동아리 1주차에는 동료의 사용 피드백을 받아 오류를 수정한다. 2주차에는 개선한 앱을 같은 배포 주소에 반영하고 최종 결과물을 정리한다. 기존 보고서·교재·영상 과제는 이미 안내한 제출 기준에 따라 함께 정리하며, 오늘 웹앱은 개인 프로젝트로 연결한다. 시험 70점 이상 기준과 시험 일정·제출기한은 확정된 안내문을 기준으로 설명한다. 오늘 수업에서 미확정 날짜를 새로 만들지 않는다.

강사용 마무리 멘트: “오늘은 디자인한 화면을 파일로 꺼내고, GitHub에 저장하고, Netlify에서 실행할 수 있는 주소로 만드는 과정을 배웠습니다. 여러분의 과제는 자신의 문제를 해결하는 작은 앱입니다. 학습동아리 방에 배포 주소와 코드 주소를 함께 올리고 사용 방법을 적어 주세요. 동료가 사용하면서 발견한 불편을 개선한 기록도 남겨 주세요. 기능 수보다 목적에 맞게 작동하고 수정할 수 있는지가 중요합니다.”

## 11. 실제 공개한 강사 시연 사례

- 공개 웹앱: https://chageun-step-by-step.netlify.app/
- 공개 GitHub: https://github.com/armin1108-hue/chageun-step-by-step
- 원본 디자인 백업: 저장소의 `source/stitch/`에 12개 HTML을 보관했다. 실제 웹앱에는 `web/`만 배포한다.
- 화면: 처음·나의 하루·마음 전하기·말로 전하기·생활 연습·쉬어 가기와 같은 브라우저의 시연 기록.
- 이 사례의 빌드 설정: `main`, Base directory 공란, `npm run build`, Publish directory `dist`, Node.js 22. 외부 npm 의존성 없이 `web/`을 `dist/`로 복사하는 빌드다.
- GitHub 코드 변경이 Netlify 자동 재배포로 이어지는 것을 확인했다. 확장자가 없는 Netlify 주소에서도 저장 기능이 작동하도록 수정했다.

수업에서 바로 실행할 기능 확인:

1. ‘나의 하루’에서 일과 두 개를 완료하고 새로고침한다. 5개 중 2개가 유지되는지 본다.
2. ‘마음 전하기’에서 감정을 고르고 크게 표시한 뒤 다시 선택한다.
3. ‘말로 전하기’에서 그림 카드 두 개를 조합하고 한 개를 지운다.
4. ‘생활 연습’에서 손 씻기 완료를 누른다. 시연 기록 보기에서 횟수와 활동을 확인한다.
5. ‘쉬어 가기’에서 호흡을 시작·멈추고 합성 소리의 재생 상태와 음량을 바꾼다.
6. 시연 기록에서 CSV 내려받기를 실행한다.

위 기능은 공개 배포에서 브라우저로 확인했다. 한국어 음성의 실제 발음과 소리 품질은 수업 PC·휴대폰에서 추가 확인한다. 기록은 접속한 브라우저에만 저장되며 실제 교사 알림·학교 DB·계정 로그인·IEP 자동평가는 구현되어 있지 않다. 실습에는 가상자료만 사용한다.

강사는 화면 확보 과정도 설명한다. ZIP 내보내기는 완료되지 않아 홈의 View Code 복사와 화면의 HTML을 확보하는 방법을 사용했다. 그 경위는 `source/provenance.json`에 남겼다. 배포 성공을 ZIP 다운로드 성공으로 설명하지 않는다.
